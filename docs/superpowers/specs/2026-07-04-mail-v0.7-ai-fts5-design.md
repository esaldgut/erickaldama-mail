# v0.7 — FTS5 en los AI tools: diseño

**Fecha:** 2026-07-04 · **Rama:** `mail-v0.7-ai-fts5` (worktree, base `develop` `a7afe66`) · **Metodología:** `subproject-delivery-canonical` (7º fogueo).

**Objetivo:** que los AI tools (`internal/aiassist`) busquen correos con **FTS5** (el cache local de v0.5,
`internal/cache`) en vez de la búsqueda substring actual, con **fallback a substring sobre DynamoDB live**
cuando el cache no está disponible. El agente AI gana búsqueda por sender+subject, ranking bm25, prefix-match
e historia completa del cache — sin quedar nunca ciego si el cache falla.

**Ancla de research (F0):** dos mapas con evidencia binaria (aiassist substring + cache FTS5 API), verificados
por el controlador contra el código real del HEAD `a7afe66`. Hechos load-bearing confirmados abajo.

---

## 1. Contexto verificado (F0)

**El estado actual (evidencia binaria):**
- `internal/aiassist` **NO importa** `internal/cache` (grep vacío). La búsqueda del agente es substring sobre
  DynamoDB, no FTS5.
- El tool de búsqueda es `search_subject` (`tools.go:60-74`): `reader.List(ctx, mb, 100, nil)` (DynamoDB Query
  directo, newest-first, **límite 100 fijo, sin paginar**) + `strings.Contains(strings.ToLower(h.Subject),
  strings.ToLower(q))` — **solo sobre `Subject`**, sin ranking.
- El tool devuelve `json.Marshal([]mailbox.Header)` → `string` (`tools.go:73`). Ese es el shape que el LLM
  consume.
- El cache FTS5 ya existe y es probado: `(*cache.Cache).Search(mailbox, query string, limit int)
  ([]mailbox.Header, error)` (`query.go:49-59`) — indexa **sender Y subject** (`schema.go:17`,
  `fts5(sender, subject, content='')`), `ORDER BY rank` (bm25), aplica `EscapeFTS` internamente
  (`query.go:56`; el consumidor pasa query cruda), devuelve **el mismo tipo `[]mailbox.Header`** que el tool
  ya serializa → **drop-in a nivel de tipo**.
- `EscapeFTS(q string) string` (`escape.go:20-26`): envuelve en comillas (neutraliza operadores FTS5) + añade
  prefix `*` fuera de la comilla (`transfer`→`transferencia`); caso especial `""` sin `*`.
- La búsqueda FTS5 **vive solo en el cache local**. Políticas de fallo existentes: `mail search` **aborta** si
  el cache falla (`main.go:516-522`, no hay equivalente live); `mail ls` **cae a DynamoDB live** (`main.go:166`);
  la TUI **degrada al filtro nativo** (`model.go:190-193`, nil-safe).
- Un consumidor read-only (aiassist) **no ve** la complejidad contentless (el `'delete'` + valores viejos vive
  solo en `Sync`, ruta de escritura; `Search`/`List` son `SELECT ... MATCH` normales).
- Único call site del agente con tools: **`mail ai agent`** (`main.go:476`, `RunAgent(ctx, p, r, mailboxName,
  goal, 10)`). NO hay binding de aiassist en la TUI.
- **Cero tests aseran `search_subject`** hoy (grep vacío). El único contrato rígido de `execTool` es
  `TestReadMessageRedactsBody` (redacción de `read_message`).

**Decisiones del usuario (cerradas en F1 brainstorm):**
1. **Alcance:** `sender+subject` vía FTS5 → renombrar `search_subject`→`search_messages` + actualizar description.
2. **Fallback:** cache abre → FTS5; cache falla/vacío → substring sobre DynamoDB live (el agente nunca queda ciego).
3. **Inyección:** interfaz `Searcher` abstracta (resuelve además el vacío de testing).
4. **Fallback en runtime:** un `fallbackSearcher` compuesto que cae a substring **solo ante error de infra del
   cache** (0 resultados de FTS5 NO dispara fallback — es respuesta válida).
5. **`limit`:** default 50, **expuesto al LLM** en el tool spec.
6. **Sync:** best-effort al arrancar el agente (índice fresco, consistente con `mail search`).

## 2. Arquitectura

Una interfaz `Searcher` en `internal/aiassist`, tres implementaciones y un compuesto. `execTool` deja de
conocer las fuentes: recibe un `Searcher` (además del `*mailbox.Reader` que los otros dos tools siguen usando).

### Nuevo archivo `internal/aiassist/search.go`

```go
package aiassist

import (
	"context"
	"fmt"
	"os"
	"strings"

	"erickaldama-mail/internal/cache"
	"erickaldama-mail/internal/mailbox"
)

// Searcher busca correos por sender/subject y devuelve headers. La firma lleva ctx porque el
// substring backend lo necesita para reader.List; el cache lo ignora hoy pero la firma se mantiene
// uniforme y a prueba de futuro.
type Searcher interface {
	Search(ctx context.Context, mb, query string, limit int) ([]mailbox.Header, error)
}

// ftsSearcher — FTS5 (sender+subject, bm25, prefix). Envuelve *cache.Cache. cache.Search ya escapa la query.
type ftsSearcher struct{ c *cache.Cache }

func (s *ftsSearcher) Search(_ context.Context, mb, query string, limit int) ([]mailbox.Header, error) {
	return s.c.Search(mb, query, limit)
}

// substringSearcher — el comportamiento actual (fallback): reader.List(limit) + Contains sobre Subject.
type substringSearcher struct{ r *mailbox.Reader }

func (s *substringSearcher) Search(ctx context.Context, mb, query string, limit int) ([]mailbox.Header, error) {
	if s.r == nil {
		return nil, nil
	}
	hs, _, err := s.r.List(ctx, mb, int32(limit), nil)
	if err != nil {
		return nil, err
	}
	var hits []mailbox.Header
	lq := strings.ToLower(query)
	for _, h := range hs {
		// stdlib case-insensitive contains — handles Unicode; NO hand-rolled toLower (audit).
		if strings.Contains(strings.ToLower(h.Subject), lq) {
			hits = append(hits, h)
		}
	}
	return hits, nil
}

// fallbackSearcher — FTS5 si el cache funciona, substring SOLO ante error de infra del cache.
// Un resultado de 0 filas sin error NO dispara fallback (es una respuesta válida "sin coincidencias").
type fallbackSearcher struct {
	cache *cache.Cache      // nil → siempre substring
	sub   *substringSearcher
}

func (f *fallbackSearcher) Search(ctx context.Context, mb, query string, limit int) ([]mailbox.Header, error) {
	if f.cache != nil {
		hs, err := f.cache.Search(mb, query, limit)
		if err == nil {
			return hs, nil // incluye 0 resultados = respuesta válida
		}
		// err REAL de infra (DB corrupta/bloqueada) → log a stderr (nunca al LLM) + cae a substring.
		fmt.Fprintf(os.Stderr, "warning: FTS5 search failed, falling back to substring: %v\n", err)
	}
	return f.sub.Search(ctx, mb, query, limit)
}

// NewFallbackSearcher construye el Searcher compuesto. nil-safe: cache==nil → siempre substring.
func NewFallbackSearcher(c *cache.Cache, r *mailbox.Reader) Searcher {
	return &fallbackSearcher{cache: c, sub: &substringSearcher{r: r}}
}
```

**Invariantes de arquitectura:**
- **AR-1:** `fallbackSearcher.Search` cae a substring **solo si `cache.Search` devuelve `error != nil`** o
  `cache == nil`. Un `([]Header{}, nil)` (0 resultados) se devuelve tal cual, NUNCA cae a substring.
- **AR-2:** `execTool` recibe un `Searcher` opaco; no conoce `ftsSearcher`/`substringSearcher`/el cache. La
  selección de impl y la construcción viven en el wire.
- **AR-3:** los warnings del fallback van a **stderr**, nunca al contexto del LLM.
- **AR-4:** `Searcher` lleva `ctx` uniforme; el substring lo usa, el FTS lo ignora.

## 3. El cambio en el tool + contrato con el LLM

### `internal/aiassist/tools.go`

**Rename y description** (esto se serializa al system prompt de Claude/Ollama):

```go
// ReadOnlyTools() — el spec de search cambia:
{
	Name:        "search_messages",
	Description: "Search messages by sender or subject (full-text, ranked best-first, prefix match). " +
		"Returns matching headers as JSON.",
	Parameters: /* JSON schema */ {
		"type": "object",
		"properties": {
			"query": {"type": "string", "description": "Search terms (sender or subject)."},
			"limit": {"type": "integer", "description": "Max results (default 50)."},
		},
		"required": ["query"],
	},
}
```

**El case** (reemplaza `case "search_subject"` en `execTool`):

```go
case "search_messages":
	q, _ := call.Args["query"].(string)
	limit := 50
	if l, ok := call.Args["limit"].(float64); ok && l > 0 { // JSON round-trip → float64
		limit = int(l)
	}
	hs, err := deps.searcher.Search(ctx, mb, q, limit)
	if err != nil {
		return fmt.Sprintf("error: %v", err)
	}
	b, _ := json.Marshal(hs)
	return string(b)
```

**Contrato con el LLM:**
- **CT-1:** el tool se llama `search_messages` (ya no `search_subject`); busca sender+subject; description
  actualizada con las 3 capacidades (sender+subject, ranking, prefix).
- **CT-2:** `limit` opcional, default **50**, expuesto en el spec. `limit` llega como `float64` (JSON), se
  convierte a `int`; `limit <= 0` o ausente → 50.
- **CT-3:** salida SIN CAMBIOS de formato: `json.Marshal([]mailbox.Header)` → string. `cache.Search` devuelve
  el mismo tipo, así que el shape que ve el LLM es idéntico (`{pk, sk, messageId, s3Key, from, subject, date}`).
- **CT-4:** query cruda, sin escapar por el tool (`cache.Search` aplica `EscapeFTS` internamente; el substring
  hace `ToLower` + `Contains`).

**`execTool` recibe `deps`** (nuevo struct pequeño, ver §4) con `searcher Searcher` + `reader *mailbox.Reader`.
Los otros dos tools NO cambian su lógica: `list_messages` y `read_message` siguen usando `deps.reader` directo,
`read_message` conserva `redact.Redact` (contrato rígido `TestReadMessageRedactsBody`).

## 4. Wire / call sites + manejo de errores

### `internal/aiassist/agent.go` — la firma de `RunAgent` crece

```go
// ANTES: func RunAgent(ctx, p LLMProvider, r *mailbox.Reader, mailbox, goal string, maxIters int) (string, error)
// DESPUÉS:
func RunAgent(ctx context.Context, p LLMProvider, r *mailbox.Reader, searcher Searcher, mailbox, goal string, maxIters int) (string, error)
```

`execTool` pasa a recibir un `deps` que agrupa reader+searcher (evita threadear dos parámetros por el loop):
```go
type toolDeps struct {
	reader   *mailbox.Reader
	searcher Searcher
}
// func execTool(ctx context.Context, call ToolCall, deps toolDeps, mailbox string) string
```
`RunAgent` arma `deps := toolDeps{reader: r, searcher: searcher}` una vez y lo pasa a cada `execTool`.

### `cmd/mail/main.go` — el único call site (`mail ai agent`, ~line 476)

```go
// Construir el Searcher compuesto: cache best-effort + Sync, fallback substring nil-safe.
var searcher aiassist.Searcher
if cachePath, perr := cache.DefaultPath(); perr == nil {
	if ca, cerr := cache.Open(cachePath); cerr == nil {
		defer ca.Close()
		// cache.Sync firma real (verificado sync.go:34): Sync(ctx, r HeaderLister, mailbox string,
		// limit int32) (int, error). Usa cache.SyncPageLimit (500) como mail search. best-effort.
		if _, serr := ca.Sync(ctx, r, mailboxName, cache.SyncPageLimit); serr != nil {
			fmt.Fprintf(os.Stderr, "warning: cache sync failed, AI search may be stale: %v\n", serr)
		}
		searcher = aiassist.NewFallbackSearcher(ca, r) // cache abre → FTS5 con fallback
	} else {
		fmt.Fprintf(os.Stderr, "warning: cache unavailable, AI search falls back to substring: %v\n", cerr)
		searcher = aiassist.NewFallbackSearcher(nil, r) // cache==nil → siempre substring
	}
} else {
	searcher = aiassist.NewFallbackSearcher(nil, r)
}
out, err := aiassist.RunAgent(ctx, p, r, searcher, mailboxName, goal, 10)
```

**Manejo de errores en capas:**

| Caso | Comportamiento | Invariante |
|---|---|---|
| Cache no abre / path falla | warning stderr + `Searcher` substring-only. Agente busca, más limitado, nunca ciego. | ER-1 |
| Cache abre, Sync falla, índice NO vacío | warning stderr + FTS5 sobre índice viejo. Aceptable. | ER-2 |
| Cache abre, Sync falla, índice VACÍO (cold-start) | warning stderr + **substring** (no FTS-vacío). El wire cuenta `n`: `serr!=nil && n==0` → `NewFallbackSearcher(nil, r)`. Cierra "nunca ciego" en el primer arranque (AUDIT FIX H8). | ER-2b |
| `cache.Search` error de infra en runtime | `fallbackSearcher` cae a substring en esa llamada (warning stderr). | AR-1, ER-3 |
| `cache.Search` 0 resultados sin error | devuelve `[]`, NO fallback. LLM ve "sin coincidencias". | AR-1, ER-4 |
| substring (fallback) también falla | `execTool` devuelve `error: %v` al LLM (comportamiento actual preservado). | ER-5 |

**Lo que NO cambia:** `Summarize`/`Draft` (no usan tools ni searcher), `wire.Provider`/`wire.Reader`, los
providers claude/ollama, el loop de `RunAgent` salvo su firma, `read_message`/`list_messages`.

## 5. Testing

La interfaz `Searcher` convierte el vacío de test de F0 en una ventaja: se testea con fakes deterministas,
sin SQLite ni mocks de DynamoDB.

### Tests del tool (con `Searcher` fake) — `tools_test.go`

```go
type fakeSearcher struct {
	gotMailbox, gotQuery string
	gotLimit             int
	ret                  []mailbox.Header
	err                  error
}
func (f *fakeSearcher) Search(_ context.Context, mb, q string, n int) ([]mailbox.Header, error) {
	f.gotMailbox, f.gotQuery, f.gotLimit = mb, q, n
	return f.ret, f.err
}
```

- **TS-1 `TestSearchMessagesUsesSearcher`** — el tool pasa `query` cruda + `limit` + `mailbox` al `Searcher`, y
  devuelve el JSON de `[]mailbox.Header` (asere `fs.gotQuery/gotLimit/gotMailbox` + unmarshal del output).
- **TS-2 `TestSearchMessagesDefaultLimit`** — sin `limit` en Args → `Searcher` recibe `limit==50`.
- **TS-3 `TestSearchMessagesLimitFromLLM`** — `limit: 5.0` (float64) → `Searcher` recibe `5`.
- **TS-4 `TestSearchMessagesSearcherError`** — `Searcher` devuelve error → output `"error: ..."` al LLM.

### Tests del `fallbackSearcher` (la lógica del compuesto) — `search_test.go` (NUEVO)

Dos fakes internos (`fakeCacheSearch` que simula `cache.Search`, `fakeSub` que cuenta invocaciones) para aislar
el compuesto sin SQLite/DynamoDB reales. **Nota de implementación:** como `fallbackSearcher` llama a
`*cache.Cache` concreto (no una interfaz), estos tests o bien usan un `*cache.Cache` real sobre un tmpdir
sqlite (ligero), o el `fallbackSearcher` se estructura para aceptar una función/closure de búsqueda inyectable.
Decisión para el plan (F3): estructurar `fallbackSearcher` con un campo `ftsSearch func(mb,q string,n int)
([]mailbox.Header, error)` inyectable (nil → substring), de modo que el `cache.Cache` real solo se cablee en el
wire y los tests inyecten un fake. Esto mantiene AR-1 testeable sin abrir SQLite.

- **TF-1 `TestFallbackUsesFTSWhenCacheOK`** — el fts fake devuelve `(headers, nil)` → NO se invoca substring.
- **TF-2 `TestFallbackZeroResultsNoFallback`** — el fts fake devuelve `([]{}, nil)` → devuelve `[]`, substring
  NO invocado (**el test con dientes**: si el fallback cae ante 0 resultados, este test FALLA).
- **TF-3 `TestFallbackOnInfraError`** — el fts fake devuelve `(nil, err)` → substring SÍ invocado.
- **TF-4 `TestFallbackNilFTSUsesSubstring`** — sin fts (nil) → substring siempre.

### Tests del `substringSearcher` — `search_test.go`

- **TS-5 `TestSubstringSearcherMatchesSubject`** — con el `fakeDDB`/`fakeS3` existentes (F0 los mapeó en
  `tools_test.go`), asere que `substringSearcher` reproduce el comportamiento actual (Contains case-insensitive
  sobre Subject, respeta el limit).
- **TS-6 `TestSubstringSearcherNilReader`** — `reader==nil` → `(nil, nil)` (para tests del tool sin AWS).

### `ftsSearcher` — integración ligera

- **TI-1 `TestFTSSearcherWiring`** (opcional) — abre un `cache.Open` en tmpdir, `Sync` un header sintético,
  `ftsSearcher.Search` lo encuentra. Confirma el cableado, no re-testea FTS5 (ya probado en `internal/cache`).

### Contrato rígido preservado

- **`TestReadMessageRedactsBody`** verde sin tocarse (no toco `read_message`).
- **`TestRunAgentExecutesToolThenAnswers`** / **`TestRunAgentCapsIterations`** — se actualizan para pasar un
  `Searcher` fake a la nueva firma de `RunAgent`; el comportamiento aserido (ejecutar tool → responder; cap de
  iteraciones) no cambia.

### Cobertura de mutación (lección de v0.6)

- **TF-2 debe tener DIENTES**: en F4 se verifica con un experimento de mutación — cambiar el fallback a "cae
  ante 0 resultados" DEBE hacer FALLAR `TestFallbackZeroResultsNoFallback` (revertir el guard → test falla →

## 7. Invariantes (resumen para el plan)

**Arquitectura:** AR-1 (fallback solo ante error de infra, NO ante 0 resultados), AR-2 (`execTool` ve un
`Searcher` opaco), AR-3 (warnings a stderr, nunca al LLM), AR-4 (`ctx` uniforme).

**Preservados:** `read_message` + `redact.Redact` (`TestReadMessageRedactsBody`), `list_messages`,
`Summarize`/`Draft`, el loop de `RunAgent` (cap de iteraciones), los providers.
