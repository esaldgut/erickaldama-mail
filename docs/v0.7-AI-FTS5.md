# v0.7 — FTS5 en las tools del agente AI (runbook)

Runbook operativo de la búsqueda que usa el agente AI (`mail ai agent`) — qué cambió respecto a v0.5,
cómo decide entre FTS5 y substring, cómo reproducir el smoke E2E, y el hallazgo de despliegue más
valioso de esta entrega. Complementa `CHANGELOG.md` (narrativa de diseño), `docs/v0.5-CACHE.md`
(el cache que esta versión reutiliza) y `docs/superpowers/specs/2026-07-04-mail-v0.7-ai-fts5-design.md`
(spec técnico completo).

---

## 1. Qué es

Antes de v0.7, la tool de búsqueda del agente AI (`search_subject`) hacía un scan de substring en
memoria sobre `Subject`, trayendo headers en vivo de DynamoDB en cada llamada — sin usar el cache
FTS5 que v0.5 ya había construido para `mail search` y el filtro `/` de la TUI. Era una inconsistencia
documentada y diferida en `docs/v0.5-CACHE.md` §8(d).

v0.7 cierra esa brecha: la tool se renombra `search_messages`, busca sobre **sender + subject** (antes
solo subject), usa el ranking FTS5 (bm25) + prefix match del cache local — el mismo camino que `mail
search` — y **solo** cae a un substring en vivo sobre DynamoDB si la infraestructura del cache falla.
Nunca busca a ciegas: siempre hay un backend capaz de encontrar correo existente.

## 2. Arquitectura — `Searcher` / `fallbackSearcher`

```go
// internal/aiassist/search.go
type Searcher interface {
    Search(ctx context.Context, mb, query string, limit int) ([]mailbox.Header, error)
}
```

Dos implementaciones:

- **`substringSearcher`** — el comportamiento histórico, ahora usado solo como fallback. Envuelve el
  `*mailbox.Reader` en vivo: `reader.List(ctx, mb, limit, nil)` + `strings.Contains` case-insensitive
  sobre **From O Subject** (antes de la corrección de F5, solo Subject — ver §5). Query vacía → `nil,
  nil` (ningún resultado), no "todo" — necesario para no divergir del comportamiento de FTS con el
  mismo input (ver §5).
- **`fallbackSearcher`** — el compuesto que decide cuál usar:

```go
// internal/aiassist/search.go
type fallbackSearcher struct {
    ftsSearch func(mb, q string, n int) ([]mailbox.Header, error) // inyectable: nil o cache.Search
    sub       Searcher                                            // substringSearcher en producción
}

func (f *fallbackSearcher) Search(ctx context.Context, mb, query string, limit int) ([]mailbox.Header, error) {
    if f.ftsSearch != nil {
        hs, err := f.ftsSearch(mb, query, limit)
        if err == nil {
            return hs, nil // incluye 0 resultados = respuesta válida (AR-1)
        }
        fmt.Fprintf(os.Stderr, "warning: FTS5 search failed, falling back to substring: %v\n", err)
    }
    return f.sub.Search(ctx, mb, query, limit)
}
```

`NewFallbackSearcher(c *cache.Cache, r *mailbox.Reader) Searcher` construye el compuesto: si `c` es
`nil`, el closure `ftsSearch` queda `nil` y el compuesto **siempre** usa substring — nil-safe por
diseño (ni un solo `if cache == nil` disperso en el resto del código).

**Regla AR-1 — nunca-ciego con fallback incorrecto:** el fallback a substring dispara **solo** cuando
`ftsSearch` es `nil` o devuelve `error != nil` (un fallo real de infraestructura — DB corrupta,
bloqueada, etc). Un resultado de **0 filas sin error** es una respuesta válida — "sin coincidencias" —
y se devuelve tal cual al LLM. Confundir "0 resultados" con "el backend falló" habría hecho que toda
búsqueda sin match cayera innecesariamente a substring, además de esconder al usuario cuándo el cache
realmente está roto.

El límite (`limit`) lo normaliza el **caller** (`execTool`, en `internal/aiassist/tools.go`) antes de
llegar al `Searcher`: `<=0 → 50` (default), `>1000 → 1000` (clamp). El clamp existe porque un LLM puede
enviar cualquier valor en el parámetro `limit` de la tool call — sin él, un `limit` gigante desbordaría
`int32(limit)` en `substringSearcher` (que lo pasa a `reader.List(ctx, mb, int32(limit), nil)`) y
produciría un valor negativo en vez de un error claro.

## 3. Cómo decide el wire: FTS vs. substring (la historia de H8-SYNC-N-1)

El wire de `mail ai agent` (`cmd/mail/main.go`, subcomando `agent`) abre el cache **best-effort**,
lo sincroniza, y decide qué `Searcher` construir según el **estado real** del índice — no según cuántas
filas trajo la sincronización de esta llamada:

```go
// cmd/mail/main.go (case "agent")
_, serr := ca.Sync(ctx, r, mailboxName, cache.SyncPageLimit)
if serr != nil {
    fmt.Fprintf(os.Stderr, "warning: cache sync failed, AI search may be stale: %v\n", serr)
}
useFTS := true
if serr != nil {
    if existing, lerr := ca.List(mailboxName, 1); lerr != nil || len(existing) == 0 {
        useFTS = false
    }
}
if useFTS {
    searcher = aiassist.NewFallbackSearcher(ca, r)
} else {
    fmt.Fprintf(os.Stderr, "warning: cold cache + sync failed, AI search falls back to substring\n")
    searcher = aiassist.NewFallbackSearcher(nil, r)
}
```

**Por qué no basta con mirar el valor que devuelve `Sync`.** `(*cache.Cache).Sync` devuelve
`n = len(hs)` — la cantidad de filas que trajo de DynamoDB **en esta llamada** (`internal/cache/sync.go`),
no el tamaño del índice SQLite ya existente. El primer borrador del guard hacía:

```go
if serr != nil && n == 0 {
    // substring
} else {
    // FTS
}
```

Esto es un **MAYOR** cazado en la auditoría 6-ejes por-tarea (F4, hallazgo **H8-SYNC-N-1**): un índice
**tibio** (filas ya indexadas por una sincronización exitosa anterior) combinado con un `r.List` que
falla **en esta llamada** produce `Sync → (0, err)` → `n == 0` → el guard viejo tomaba la rama de
substring, **descartando un índice FTS perfectamente usable** solo porque la sincronización de hoy no
trajo filas nuevas. El propio comentario del código decía "un índice no vacío con un Sync fallido usa
FTS (obsoleto-pero-usable)" — el guard basado en `n` lo contradecía.

**El fix:** en vez de confiar en `n`, cuando `Sync` falla se **prueba el estado real** del índice con
`ca.List(mb, 1)` — "¿tiene esta mailbox al menos 1 fila indexada?". Si sí, el índice es usable (obsoleto
pero mejor que nada) → FTS. Si no (o el probe mismo falla), el índice está realmente vacío → substring.

| `Sync` falló? | Índice tiene filas (probe `List`)? | Comportamiento viejo (sobre `n`) | Comportamiento nuevo (sobre estado real) |
|---|---|---|---|
| No | — | FTS | FTS |
| Sí | Sí (índice tibio, esta llamada no sumó filas) | **BUG:** substring (descarta índice usable) | **FIX:** FTS (obsoleto-pero-usable) |
| Sí | No (nunca sincronizado, índice vacío) | substring (correcto) | substring (correcto) |
| Sí | Sí (esta llamada sumó algo antes de fallar) | FTS (correcto) | FTS (correcto) |

**Nota meta — validar incluso la propia sugerencia del auditor.** La primera corrección que propuso el
propio ciclo de auditoría era un guard "fail-open" que habría **reintroducido la ceguera de cold-start**
(usar FTS también cuando el índice está genuinamente vacío). Se verificó la sugerencia contra el código
real antes de aplicarla y se descartó a favor del probe explícito — "validar, no confiar, incluso al
revisor" (la misma disciplina que cazó defectos de reviewers en v0.6).

## 4. Los otros hallazgos de la auditoría en capas

Cada capa de revisión cazó una clase de defecto que las otras, estructuralmente, no podían ver:

- **F3 — auditoría del plan** (compila contra el código real antes de ejecutar el plan): un **CRIT** de
  shadowing — el parámetro `mailbox` de la interfaz `Searcher` y de `substringSearcher.Search` sombreaba
  el nombre del paquete `mailbox` (`erickaldama-mail/internal/mailbox`), lo que rompía cualquier
  referencia a `mailbox.Header` dentro del cuerpo del método. Renombrado a `mb` en toda la interfaz y sus
  implementaciones. Además, un **MAYOR**: sin clamp, un `limit` enorme enviado por el LLM desbordaría
  `int32(limit)` a un valor negativo — se agregó el clamp a 1000 en `execTool` (§2).

- **F4 — auditoría 6-ejes por-tarea** (el wire, Task 6): el hallazgo **H8-SYNC-N-1** descrito en §3.

- **F5 — revisión de rama completa** (ojos frescos, sin el contexto de las tasks individuales): un
  **IMPORTANT** cross-package invisible a las revisiones por-tarea — los dos backends de `Searcher`
  no coincidían en qué significa "buscar". El índice FTS cubre `sender`+`subject` (esquema
  `fts5(sender, subject)` de v0.5) y la tool promete "sender or subject", pero `substringSearcher`
  matcheaba **solo Subject** (nunca From); y con query vacía, FTS no matchea nada mientras que substring
  matchea **todo** (`strings.Contains(x, "")` es siempre `true` en Go). Causa raíz: el rename
  `search_subject`→`search_messages` amplió el contrato de la tool, pero solo el lado FTS lo cumplía de
  verdad. Fix (commit `51a3c67`): `substringSearcher` ahora matchea From **o** Subject, y una query vacía
  devuelve `nil` (sin resultados) en vez de todo el listado — paridad de campo entre ambos backends.

## 5. Contrato intacto: `read_message` sigue redactando el body

`search_messages` devuelve el `[]mailbox.Header` serializado a JSON — esto incluye los campos `from`,
`subject`, `pk`, `sk`, `messageId`, `s3Key`, `date` (todos los tags del struct `Header`). **Es exactamente
la misma superficie que el `search_subject` viejo** (que también hacía `json.Marshal([]Header)`): v0.7 NO
expone ningún campo nuevo — no es una regresión. Lo que la tool de búsqueda **nunca** expone es el cuerpo
del mensaje (S3); ese solo llega vía `read_message`, y ahí el test `TestReadMessageRedactsBody` verifica
que el body crudo pasa por `redact.Redact` **antes** de reingresar al loop del agente. Ese invariante de
redacción no cambió con v0.7; la nueva superficie de búsqueda no introduce una segunda vía de fuga del
cuerpo. (Nota de precisión, del review externo del PR: el `s3Key` que viaja en el header es la misma clave
que `read_message` ya toma como argumento — no es un secreto, es el identificador del mensaje.)

## 6. Smoke E2E — 2 capas, contra el sistema real

Corrido contra la cuenta AWS real (`<ACCOUNT_ID>`, perfil `mail-client-read`) con un cache FTS5 tibio
(sincronizado desde una sesión anterior) y el backend local Ollama corriendo **`qwen2.5:7b`** — **no**
el modelo por defecto del cliente (`qwen3:32b`); hubo que pasar `--agent-model qwen2.5:7b` explícito.

**Comandos para reproducir** (mailbox y goal de ejemplo — sustituir por los reales del operador):

```bash
# 0. Prerrequisito: cache FTS5 tibio (o dejar que "mail ai agent" lo sincronice best-effort)
mail search --mailbox inbox "example"

# 1. Ollama corriendo el modelo NO-default usado en el smoke
ollama serve &
ollama pull qwen2.5:7b

# 2. Layer 2 — loop LLM real: el agente invoca search_messages -> FTS5 -> respuesta en lenguaje natural
mail ai agent --agent-model qwen2.5:7b --mailbox inbox \
  "Find any message from a sender containing 'example' and tell me the subject"
```

**Layer 1 — harness determinístico sobre el `Searcher` real** (probó el comportamiento real del índice
FTS5, no un mock):

- Match de subject: query `"payment"` → 1 hit.
- **Prefix match:** query `"transfer"` encontró un subject tipo `"...transference..."` — confirma que es
  prefix FTS5 del último token, no un substring plano (§8(e) de `docs/v0.5-CACHE.md`).
- **Paridad sender+subject:** una query por término de remitente devolvió hits rankeados que coinciden
  con el campo `From` — confirma que el fix de field-parity de F5 (§4) funciona sobre el índice real, no
  solo en el test unitario.
- Semántica AND: una query de 2 términos que no debía matchear nada → 0 resultados.
- Query vacía → 0 resultados.

**Layer 2 — loop LLM real:** `mail ai agent "<goal>"` → qwen invocó `search_messages` → FTS5 resolvió →
el agente devolvió una respuesta en lenguaje natural correcta, citando el subject real encontrado.

## 7. Deploy finding — qwen inventa operadores estilo Gmail

**Este es el hallazgo con más valor de la entrega — solo un smoke E2E real contra un LLM real pudo
revelarlo.** Ningún test unitario ni mock lo habría cazado, porque el defecto no está en el código de
v0.7: está en cómo un modelo local decide llamar a la tool.

**Qué pasó:** al pedirle al agente que buscara correo por remitente, `qwen2.5:7b` invocó
`search_messages` con `query="from:amazon"` — inventando un operador de campo estilo Gmail
(`from:`, `subject:`) que la tool **no** soporta ni documenta. FTS5 buscó el término literal
`"from:amazon"` (los dos puntos no son un operador para SQLite FTS5, son parte del token) → 0 hits.

**Por qué NO es un bug de v0.7:** se re-ejecutó el mismo goal instrumentando la query enviada, y con un
query limpio `query="amazon"` (sin el prefijo inventado) el mismo índice devolvió 3 hits, con los 3
subjects listados correctamente. El código de búsqueda funciona — el modelo local asumió una sintaxis
de operadores que ninguna instrucción de la tool prometía.

**Por qué AR-1 se sostuvo correctamente:** `search_messages` con `query="from:amazon"` devolvió `0`
resultados **sin error** — exactamente el caso "0 resultados es una respuesta válida" de §2. No hubo
fallback espurio a substring (que además tampoco habría encontrado nada útil buscando el string literal
`"from:amazon"`). El agente reportó honestamente "no encontré coincidencias" en vez de fallar o
inventar una respuesta. El invariante nunca-ciego-nunca-mal-disparado se comportó exactamente como se
diseñó, incluso frente a un input que el diseño no anticipó.

**Mitigación para una versión futura (deuda registrada, NO bloqueante):** el `Description` de la tool
`search_messages` podría declarar explícitamente "solo términos simples, sin operadores tipo
`from:`/`subject:`" para desalentar al modelo de inventarlos; alternativamente, el wire podría detectar y
despojar prefijos de operador conocidos (`from:`, `subject:`, `to:`) antes de pasar la query a FTS5. Se
deja fuera de v0.7 porque es un ajuste de comportamiento de modelo, no una corrección de un defecto de
código — y el fallback (AR-1) ya garantiza que el peor caso es "0 resultados honestos", nunca una
respuesta incorrecta o un crash.

## 8. Limitaciones conocidas / deuda registrada

Decisiones diferidas con motivo explícito — no bugs pendientes.

**(a) PATRON-1 (MENOR) — el árbol `DefaultPath→Open→Sync` está duplicado una 4ª vez.**
`mail ls`, `mail search`, y ahora `mail ai agent` repiten (con variaciones menores de manejo de error)
el mismo patrón: resolver `cache.DefaultPath()`, `cache.Open`, `Sync` best-effort. Con v0.7 esta es la
cuarta copia parcial en el código. Candidato de refactor: extraer un helper compartido
(`internal/cache` o `internal/wire`) que las tres invocaciones consuman — diferido porque cada call-site
difiere ligeramente en qué hace si el cache no está disponible (algunos degradan a lectura en vivo,
`mail search` no tiene equivalente en vivo y aborta).

**(b) BP-1 (MENOR) — el clamp de `limit` es por convención del caller, no defensa en profundidad.**
El clamp `[1, 1000]` que evita el overflow de `int32(limit)` (§2, §4) vive en `execTool`
(`internal/aiassist/tools.go`), no dentro de `substringSearcher.Search` mismo. Hoy hay un solo caller
(`execTool`), así que el contrato se cumple, pero si en el futuro apareciera un segundo caller del
`Searcher` sin pasar por `execTool`, el overflow volvería a ser posible. Oportunidad de defensa en
profundidad diferida — no urgente mientras el único caller sea `execTool`.

**(c) Description de `search_messages` promete un contrato que el fallback no cumple del todo, y un LLM
puede interpretarla mal (registrado tras la review externa de PR + el deploy finding de §7).** El
`Description` de la tool dice "full-text, ranked best-first, prefix match" — cierto para el backend FTS,
pero **no** para el fallback `substringSearcher`: un substring plano no rankea y no hace prefix match
real (coincide con cualquier substring, no solo con el inicio del token), así que en el modo degradado el
LLM recibe un contrato que el backend activo no cumple del todo. Por separado, §7 mostró que un LLM local
(`qwen2.5:7b`) puede inventar operadores de campo estilo Gmail (`from:`, `subject:`) que la tool ni
soporta ni menciona, buscando el prefijo literalmente y devolviendo 0 hits. Mitigación registrada para
una versión futura: endurecer el `Description` ("solo términos simples, sin operadores `from:`/
`subject:`") y/o despojar prefijos de operador conocidos antes de pasar la query a FTS5. No bloqueante —
el fallback ya devuelve `0` resultados honestos en vez de una respuesta incorrecta (AR-1).

> **Actualización v0.7.1 (2026-08-06) — la primera mitigación quedó ENTREGADA.** El `Description` de
> `search_messages` se reescribió a ~4 oraciones ASCII que describen el **mecanismo** de búsqueda (no un
> resultado): *"a query such as `from:amazon` is searched as the two literal words `from` and `amazon`, not as a
> sender filter, so use plain keywords like `amazon` instead."* El smoke E2E con `qwen2.5:7b` confirmó
> `query="amazon"` limpia en 4 corridas del mismo goal que antes producía `from:amazon`. La **segunda** mitigación
> —despojar operadores en el wire (Approach B)— sigue diferida, condicionada a evidencia de un smoke donde un
> modelo siga inventando operadores pese al Description. Ver `CHANGELOG.md` §`[mail v0.7.1]`,
> `docs/ROADMAP.md` (fast-follows v0.7) y
> `docs/superpowers/specs/2026-07-28-search-messages-operator-hardening-design.md`. Nota: el smoke de v0.7.1
> también destapó un deploy finding pre-existente —el wire de `mail ai agent` no honra `cfg.Mailboxes` (AGENT-MB-1
> en el ROADMAP)— ortogonal a este §8(c).
